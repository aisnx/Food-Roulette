餐厅转盘选餐项目可行性分析
一、项目概述
产品形态：Web 网站 + App（安卓 /iOS）
核心流程：用户输入位置 / 定位 → 设置搜索半径 → 获取周边餐厅列表 → 加载到随机转盘 → 点击转盘抽取餐厅，解决 “不知道吃什么” 的决策痛点。
配套可选功能：过滤菜系、价格区间、评分、是否营业；收藏餐厅；历史抽取记录；多人随机组队抽签。
二、优势（可行性亮点）
需求真实且高频
“纠结吃什么” 是大众普遍痛点，产品定位轻量化，不是替代美团 / 大众点评，而是决策辅助工具，差异化很强。美团重在挑选对比，你的产品重在 “交给随机，减少选择内耗”，场景适合单人、同事聚餐、情侣选择。
技术路线清晰，MVP 版本开发成本可控
核心模块拆解：
定位 + 周边 POI 餐厅数据：调用第三方地图 POI 接口（高德 / 百度地图开放平台），获取餐厅名称、地址、距离、评分、营业状态；
前端转盘组件：Canvas/SVG 实现转盘动画，Web 端开发成熟，可复用到 App（WebView 或 Flutter 跨端）；
后端：用户记录、收藏列表、缓存餐厅数据，轻量服务即可；
App 方案：优先 Flutter 跨端，一套代码打包安卓 + iOS，降低双端维护成本；网站直接用 Vue/React 开发。
MVP 最小版本：网页端优先开发，不需要复杂账号系统，游客定位就能直接转盘，快速验证用户喜好，后续再做 App。
推广门槛低
属于趣味工具类，很适合社交传播：截图转盘结果分享到微信群、朋友圈。用户自发传播成本低，不需要很重的运营。
三、核心风险与难点（重点）
1. 数据接口是最大成本 & 合规卡点
高德 / 百度地图开放平台 POI 检索免费额度有限。
少量测试：免费额度够用；
用户量上来后，每次定位搜索餐厅都要调用接口，按次计费，用户一多服务器费用会快速上涨。
限制：地图 API 返回的数据不能直接存储、批量抓取，只能实时查询展示；不能把餐厅数据缓存到自己数据库长期使用，违反地图服务商协议。
备选方案：对接美团开放平台，但美团开放 API 申请门槛高、审核严格，个人开发者很难拿到权限。
2. 合规风险
定位权限：App / 网页都需要用户授权定位，不能强制获取；
餐厅信息版权：地图 POI 信息只允许实时展示，不可爬虫抓取、离线存储；
免责：餐厅营业状态、价格可能延迟，需要加提示：信息仅供参考，以商家实际情况为准，避免用户踩坑投诉；
App 上架：iOS App Store 审核对定位类、本地生活类应用审核严格。
3. 用户体验问题
同一地点餐厅过多：转盘条目太多，动画卡顿；餐厅太少则转盘选项不足；需要做数量限制（例如最多 20 个餐厅）；
重复餐厅、已关闭店铺：地图 POI 会存在失效商家，需要增加过滤条件（过滤停业、低评分店铺）；
网络依赖：必须联网拉取餐厅列表，离线无法使用。
4. 盈利难度（如果打算商业化）
纯工具类很难变现。可选变现路径：
无广告：纯兴趣项目（个人开发）；
轻度广告：网页 / App 植入广告（用户量大才有收益）；
佣金：对接团购外链，用户跳转下单拿佣金（需要和本地生活平台合作，门槛高）；
如果只是个人兴趣项目，不追求盈利，这个问题可以忽略。
四、开发优先级建议（分阶段落地）
阶段 1：MVP 网页版（推荐优先做，验证可行性）
功能：定位、设置距离范围、拉取周边餐厅、转盘随机抽取、基础筛选（评分、菜系）。
不用做 App，网页端手机就能打开，开发周期短，快速测试效果。
阶段 2：迭代优化网页
增加：收藏餐厅、历史记录、排除不想吃的餐厅。
阶段 3：Flutter 跨端 App
网页验证用户反馈好之后，再打包 App，减少前期投入浪费。
五、总结判断
✅ 技术可行，需求成立，适合作为个人项目 / 小创业项目
适合：兴趣开发、小工具产品，先网页试水；
不适合：一上来就投入大量资金开发 App，预期短期赚大钱。
